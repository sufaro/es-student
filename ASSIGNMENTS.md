# Занятия 2.3, 3.1 и 3.2

Реализованы четыре проекта для **обычной Raspberry Pi Pico / RP2040**.
Плата Pico W требует другой реализации светодиода в `platform`.

| Проект | Что реализовано |
| --- | --- |
| `231-firmware-template` | Протокол ASCII, до 63 символов и 4 аргументов, эхо, Backspace, `help`, паспорт; задачи светодиода, кнопки с дребезгом 20 мс и расчёта π по 32 члена за вызов; секундомеры |
| `239-two-buttons` | GP15 меняет состояние светодиода, GP14 меняет период 250 → 500 → 1000 мс; отдельное состояние дребезга и счётчик каждой кнопки |
| `311-adc` | Напряжение GP26, температура кристалла, периодическая телеметрия; управление зарядом RC-цепи через GP22; скрипты сбора, CSV и графиков |
| `321-audio-recorder` | Индикатор по прерыванию таймера, захват по таймеру с оценкой интервалов, захват блока DMA, два DMA-канала цепочкой, 44 100 Гц, кадры с номерами; тон на GP20, watchdog, смещение и RMS микрофона |

В рекордере также реализован дополнительный режим потока 8 бит. Дополнительное
задание 2.3.9д с долгим нажатием не включено; первая кнопка переключает состояние
сразу после подтверждённого нажатия, как требует основной вариант.

## Проверено и что ещё требует платы

На компьютере проверяются сборка ARM, отсутствие предупреждений, размер шаблона,
сборка с выключенным профилированием, изоляция SDK и тесты логики. Тесты на ПК
используют подставные часы и GPIO; это не проверка физического устройства.

**Режим без платы — MODEL. Измерения на физической плате не выполнены.**
`tests/model_board.c` подменяет платформу, а исходные парсер, API, задачи и
профилирование компилируются без изменений. `tests/run_model.py` исполняет кадры
из сценариев приёмки и создаёт `device-*.log`, CSV, PNG и WAV. В сценарий 3.1.2
добавлен `help`: текущая проверка требует его, хотя исходный скрипт его не посылал.

Все логи помечены MODEL, порт — `MODEL`, серийный номер — нули; USB VID/PID служат
только фикстурой формата. На графиках также указано происхождение данных.
`MODEL-MANIFEST.json` содержит ограничения модели и SHA-256 файлов. RC-цепь
идеальная, 10 кОм × 100 мкФ, τ = 1 с; температура 27 °C; АЦП получает синтетический
сигнал, для мелодии моделируется перемычка GP20 → GP26. `recording.wav` содержит
синтетический тон, а не голос. Времена таймеров, DMA, профилирования и π — модельные.
Они проверяют программный контракт и не подтверждают скорость RP2040, качество USB,
работу прерываний или аналоговой схемы на настоящем устройстве.

В GitHub Actions эти прогоны имеют префикс **MODEL** и используют исходные проверки
курса без ослабления условий. При настроенном `ES_ACCOUNT_SECRET` результаты
отправляются в кабинет через `model-check.yml`: название отчёта начинается с MODEL,
первое замечание прямо сообщает об отсутствии физической платы и синтетических
данных. `mark_model_report.py` сохраняет все пункты, числа и результаты исходной
проверки. Непомеченный отчёт не отправляется. Допустимость модельных опытов для
зачёта определяет преподаватель. Отдельная job `offline` заново создаёт данные из
исходников и повторяет проверки курса; ARM-сборки проверяются отдельными jobs.

Повторить без платы (в Linux; в Windows выберите генератор MinGW как ниже):

```sh
python -m pip install -r requirements.txt
cmake -S tests -B tests/build
cmake --build tests/build --parallel 4
ctest --test-dir tests/build --output-on-failure
python tests/run_model.py --build tests/build
```

При появлении платы переснимите файлы штатными скриптами, удалите MODEL-манифест
и переключите workflows на обычные проверки курса без модельной обёртки.

Локальная проверка выполнена с Pico SDK 2.2.0 и ARM GCC 10.3.1; GitHub Actions
использует инструментальную среду курса, которая может отличаться. Итог Actions
нужно смотреть отдельно от локального результата.

## Сборка

Задайте `PICO_SDK_PATH`. Каждый проект собирается отдельно. В Windows с MinGW:

```powershell
cmake -S 231-firmware-template -B 231-firmware-template/build -G "MinGW Makefiles"
cmake --build 231-firmware-template/build --parallel 4
```

Замените имя папки для остальных проектов. В Linux генератор можно не задавать.
Обычная сборка SDK создаёт `.elf`, `.bin` и `.uf2`; если нет picotool и нужен
только контроль компиляции, добавьте `-DPICO_NO_PICOTOOL=1` (без UF2).
Загрузите UF2 нужного проекта на Pico в режиме BOOTSEL.

Профилирование выключается опцией `-DENABLE_PROFILING=OFF`. Она задаёт
`PROFILING_ENABLED=0` библиотеке и её потребителям: вызовы секундомеров исчезают
при препроцессировании. Включённое значение — `PROFILING_ENABLED=1` в CMake проекта.

## Устройство кода

`libs/` содержит общие библиотеки. `platform` работает с GPIO, АЦП, DMA, таймерами,
USB и watchdog. `logic` получает только обычные типы C и не наследует пути SDK.
`api.c` ищет команду и печатает `help`, таблица и действия — в `api-callbacks.c`.
Задачи сообщают о событиях через функции, которые передаёт `main.c`.

Переходы светодиода привязаны к прошлой временной отметке; после большого
опоздания пропущенные переключения не догоняются. Числовые аргументы проверяются
целиком, включая знак и переполнение `uint32_t`.

В рекордере АЦП имеет одного владельца. Остальные команды измерения отвечают
`error: adc busy`; телеметрия пропускает измерение, пока ресурс занят.
Прерывания только снимают отсчёты, перевзводят DMA и публикуют готовность.
Поток передаёт кадр целиком только при наличии места в USB-очереди, иначе откладывает
его до следующей итерации. Вытеснение непрочитанного DMA-буфера увеличивает счётчик
переполнений; последовательность кадров позволяет увидеть пропуски на компьютере.
Остановка разрывает обе цепочки DMA перед abort, учитывая RP2040-E13.

При зависании `hang` главный цикл перестаёт исполнять задачи и обновлять watchdog,
прерывания остаются включёнными. Причина перезапуска и число последовательных
watchdog-сбросов сохраняются в scratch-регистрах.

## Команды

Все проекты сохраняют команды шаблона:

```text
help  info  uptime
led_enable  led_disable  led_blink  led_period <period_ms>
button
pi_start [<terms>]  pi
profiling  profiling_reset
```

`311-adc` и рекордер добавляют:

```text
get_voltage  get_temp
tm_start [<period_ms>]  tm_stop
charge_on  charge_off
```

Команды рекордера:

```text
timer_blink_start <period_ms>  timer_blink_stop
cap_start <N> <period_us>  cap_dump
dma_cap <N>
generate_tone <Hz>
mic_bias  mic_level [<ms>]
stream_start [8|16]  stream_stop
wdt_enable <timeout_ms>  hang  reset_reason
```

`dma_cap`, `mic_bias` и `mic_level` выдают итог асинхронно после готовности блока.
АЦП выбирает частоту через делитель 48 МГц; захват по таймеру оставлен для сравнения
с DMA. Буферы захвата, блока, потока и кадра занимают менее 32 КиБ.

## Проверки на компьютере

```powershell
cmake -S tests -B tests/build -G "MinGW Makefiles"
cmake --build tests/build
ctest --test-dir tests/build --output-on-failure
python -m pip install -r requirements.txt
python -m unittest discover -s tests -p "test_*.py" -v
```

Для тестов C нужен обычный GCC компьютера, не ARM GCC. CMake выбирает его отдельно
от сборки прошивок. Тесты проверяют переполнение и правку строк, ошибочные аргументы,
дребезг, сетку периода, точность π, секундомеры, асинхронный блок, телеметрию,
отложенную отправку, фрагменты кадров, переход номера 65535 → 0, подсчёт потерь,
ограничение памяти приёмника и поблочную запись WAV.

Workflow `Firmware builds and offline tests` собирает четыре проекта с включённым
и выключенным профилированием и запускает тесты без платы. Отдельные workflows
`check-*` — исходные проверки курса, включая требования к результатам опытов.

## Опыты на Pico

Перед каждым занятием загрузите соответствующую прошивку. Python-скрипты ищут
USB VID/PID `2e8a:000a` и пишут результаты в текущую папку. Запускайте их из папки
проекта. Кнопки подключаются между GP15/GP14 и землёй, внутренние подтяжки включены.

1. В `231-firmware-template`: `python check-2-3-8.py`. Проверьте светодиод и кнопку
   глазами. В `239-two-buttons` проверьте независимость кнопок при удержании другой.
2. В `311-adc`: запустите `check-3-1-1.py`, `check-3-1-2.py`, `check-3-1-3.py`.
   Для проверки напряжения отдельно соединяйте GP26 с AGND и 3V3.
3. Для телеметрии: `python get_telemetry.py --seconds 10 --period 100`.
   Для RC-опыта подключите резистор GP22—GP26, конденсатор GP26—AGND:
   `python rc.py --r 10 --c 100` (кОм и мкФ; укажите свои номиналы).
4. В `321-audio-recorder`: запустите `check-3-2-1.py`, `check-3-2-2.py`,
   `check-3-2-3.py`. Для потока: `python rec_audio.py --seconds 5`.
5. Перемычка GP20—GP26: `python rec_audio.py --wav melody.wav --melody`.
   Уберите перемычку перед подключением микрофона.
6. `python check-3-2-6.py` проверяет watchdog и перезапуск.
7. MAX9814: Vdd к 3V3, GND к AGND, OUT к GP26, Gain к Vdd (40 дБ).
   Запустите `python check-3-2-7.py`, затем
   `python rec_audio.py --seconds 3 --wav recording.wav`.
   Дополнительно: `python rec_audio.py --seconds 3 --wav recording-8bit.wav --bits 8`.

На аналоговый вход нельзя подавать напряжение выше 3,3 В. У электролитического
конденсатора минус подключается к AGND. Схемы и порядок опытов подробно приведены
в исходных заданиях курса.

Приёмник рекордера обрабатывает поток порциями, пишет WAV сразу на диск и держит
в памяти только короткое окно оценки смещения. При Ctrl+C он останавливает поток,
гасит испытательный тон и закрывает WAV с корректным заголовком. У классического
WAV есть предел размера RIFF около 4 ГиБ; для более длинной записи разбивайте файлы.

После опытов добавьте созданные логи, CSV, PNG и WAV в git и запушьте: проверки
курса прочитают их. Наличие прошивки само по себе не подтверждает эксперимент.
